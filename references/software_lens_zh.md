# 软件项目镜头

在 `SHAPE` 和 `STRESS TEST` 按需检查；不要把每项都变成问题。

- 架构：系统边界、组件职责、依赖和关键状态如何划分？
- 用户与场景：谁在什么情境下完成什么任务，当前采用什么替代方式，转向新方案的阻力是什么？
- 接口：输入输出、数据契约、权限、错误语义和兼容性是什么？
- UI 状态（仅适用时）：加载、空态、成功、错误、权限不足与恢复操作如何让用户理解？
- 迁移：现有数据或行为如何迁移，如何分阶段发布与回滚？
- 安全：威胁、隐私、身份与授权、密钥和合规门槛是什么？
- 性能：延迟、吞吐、容量、资源与成本预算是什么？
- 运维：可观测性、故障响应、恢复、所有权和运行手册需要什么？
- 测试：单元、集成、端到端、回归和验收如何覆盖核心及异常路径？

将每个里程碑写成可观察的用户或系统结果，并配验收检查。只有实施阶段才按端到端垂直切片组织工作：每片应能从用户入口走到可验证结果；探索、决策或风险消除阶段不必伪装成垂直切片。高风险变更优先用 spike、原型或受限发布验证关键假设。

## 执行与接续（启用 tracking 后）

- 每个可独立验收的结果对应实际改动与验证；实现结束但尚未验证时分开记录，不宣布里程碑完成。
- 接续证据至少能定位相关代码/提交或未提交工作树、实际运行的检查与结果、未覆盖的风险。记录已观察事实，不把拟运行的命令写成 PASS。
- 交接按需说明模块间消费/产出接口和必须保持的兼容约束；共用用户目标或集成验收的模块可以属于同一计划。
- 核对当前变更与证据基线；旧会话报告成功不能证明后续修改仍成功。当前任务、阻塞、验证结果与下一步写入 STATUS，详细产物保留在项目正常路径。
- 执行采用适用实现 skill 或通用开发工作流。关键事件记录由执行者遵循 [进展协议](progress_protocol_zh.md)，不要求用户反复发起手工 MAINTAIN。
